# ADR 0008 — Bytes-scaled data-plane relay, port-per-session

**Status:** Decided, Sept 9 2026. Builds on `adr/0003-rendezvous-relay-split.md` (the rendezvous/data-relay split) and `adr/0007-rendezvous-relay-metering.md` (the x402/Hedera payment pattern this reuses). Gate 4.1 (rendezvous fee) is already verified; this ADR covers the second, bytes-metered fee `adr/0003` named but didn't design (Gate 4.2), plus the price-based relay-selection half of Gate 4.3.

## Context

`adr/0003` split the relay into a rendezvous relay (flat fee, every connection attempt) and a data-plane relay (bytes-scaled fee, only used when a connection can't go direct) but left the data-plane relay's actual mechanism as future work. Two questions turned out not to have obvious answers.

**How does `brambled` decide to use the data relay?** The obvious-sounding answer — detect that hole-punching failed, then fall back — doesn't apply here: this project has no STUN/hole-punching implementation at all (`brambled/main.go`'s header comment already says so), and no gate requires building one. Re-reading Gate 4.3's own demo requirement settles this: it asks for "a topology that cannot hole-punch," which means the data relay is the *only* path for that connection, not a fallback from a failed one. An operator/demo flag that explicitly routes a specific peer through the data relay satisfies this identically to automatic failure detection, for a fraction of the code (no liveness watcher, no handshake-timeout tuning). Decision: a new `-relay peer-label=data-relay-label` flag on `brambled serve` marks specific tracked peers as relay-routed; everything else behaves exactly as before.

**How does traffic actually get multiplexed onto the relay?** The first design considered — one shared UDP port, forwarded traffic distinguished from session-control datagrams by a discriminator byte (WireGuard's real packets always start with byte 1–4: `MessageInitiationType`/`MessageResponseType`/`MessageCookieReplyType`/`MessageTransportType`, confirmed directly against `golang.zx2c4.com/wireguard/device/noise-protocol.go`) — turned out not to fit this codebase. The discriminator itself is sound, but there's no way to *use* it here: `brambled/wgnode/node.go`'s `Node` hands its outer UDP socket entirely to `wireguard-go`'s `device.Device` (via `conn.NewDefaultBind()`), and `brambled` never gets to send an out-of-band "bind" datagram from that exact socket before WireGuard's own traffic goes out to whatever endpoint it's configured with. There's no clean injection point.

## Decision

**One ephemeral UDP port per purchased session** (TURN-style port-per-allocation), not a shared multiplexed port. This sidesteps the socket-ownership problem entirely — no bind datagram is needed, because WireGuard itself starts sending handshake-init packets to the configured endpoint the moment `AddPeer` sets it, and that's all the relay needs to see.

**Session lifecycle:**

1. The buying node's local sidecar pays `POST /data-relay-session?bytes=N` on the target data relay's `relay-sidecar` (x402-gated, `@x402/hono`'s `DynamicPrice` computes the charge from `N` — confirmed present in the installed `@x402/core` types, so this is one route, not fixed size tiers).
2. On settlement, `relay-sidecar` calls a **loopback-only** HTTP endpoint on its own Go `relay` process (`POST 127.0.0.1:<internal-port>/internal/data-relay-session`) — only the Go process can open the actual UDP forwarding socket, so the TS side that handles payment has to hand off to it, the mirror image of `adr/0007`'s secret handoff (there, Go generates and hands a secret to TS; here, TS collects payment and hands a request to Go).
3. The Go relay allocates a fresh UDP port, creates in-memory session state (`id`, `port`, `bytesAllotted`, `bytesUsed`, `expiresAt`), returns it up the chain to `brambled`.
4. `brambled` builds `relayCandidate := "<relay-host>:<port>"` and calls the **existing, unmodified** `rendezvous.Exchange(relayAddr, own, peerPubkey, relayCandidate, token, ttl)`. No wire-protocol change: the candidate a node publishes is already a generic `ip:port` string the peer blindly sets as its own WireGuard peer-endpoint. Using the data relay just means publishing the relay's address instead of a real one — the peer's handling code doesn't need to know the difference. Only the flagged side buys a session; the other side needs no config at all, since it learns the relay's `ip:port` as an ordinary candidate through the unmodified exchange.
5. The relay's UDP forwarder on that port: the first two distinct source addresses become "slot A"/"slot B" (matched by exact IP:port equality). Every subsequent datagram from one slot is forwarded to the other slot's last-known address, decrementing `bytesUsed` by its payload length. Forwarding stops once `bytesUsed >= bytesAllotted`; resuming requires a fresh purchase. **Known gap, not WireGuard roaming support:** a genuine mid-session NAT remap arrives as an unmatched source and takes the other free slot (or is dropped once both are full) rather than being recognized as the same peer moving — acceptable for a stable-NAT or localhost demo, a real limitation for anything longer-lived. Also needed on top of this: WireGuard's protocol never has the passive/responder side send anything unprompted, so without a persistent keepalive (`wgnode.Node.SetPersistentKeepalive`, armed on both relay-routed peers by `brambled/main.go`'s `relayRoutedEndpoint`) only the initiating side's slot would ever get learned.

**Trust model — stated plainly, not hidden:** the ephemeral port itself is the authorization. It's allocated only after a real payment, disclosed only to the two participants (via the same rendezvous candidate-exchange channel `adr/0003`'s trust-boundary argument already covers), and short-lived. There is no per-packet cryptographic binding of a datagram to its session beyond "first two distinct sources win the two slots" — a third party who happened to guess the port during its brief lifetime could contest a slot. This is a deliberate, scoped simplification for the hackathon timeline, in the same spirit as `scripts/check-no-endpoints.mjs`'s own documented blind spot: a known limit, not a silent one. It does not weaken the mesh's actual admission boundary (`adr/0003`'s "Trust boundary" section) — a relay, honest or not, still can't complete a WireGuard handshake it doesn't hold the private key for.

**Billing: pre-paid allotment, manual top-up.** A session covers a fixed byte budget bought upfront; running out mid-transfer means buying a new session (a second real on-chain payment, sized to the remaining transfer) rather than an automatic mid-flight top-up. Automatic top-up is scoped out below — for the demo, a bigger transfer is deliberately started with a bigger upfront purchase, which is what actually exercises "cost scales with bytes" (Gate 4.2's literal test) without needing a live top-up mechanism.

**Relay selection (Gate 4.3, selection half only):** `relay-sidecar` gains an unauthenticated `GET /price` quote route. `brambled` gains a repeatable `-data-relay label=sidecar-url` flag (an operator-supplied pool, same shape as the existing `-peer`/`-forward` flags) and picks among a pool by querying `/price` from each candidate, timing the round-trip as a latency proxy, and choosing the lowest `price + latencyWeight*rtt` — a small, deliberately simple composite, implemented as a pure function (`brambled/datarelay.Pick`) so it's unit-testable without real HTTP calls.

## Explicitly out of scope this pass

- **Automatic mid-transfer top-up.** Would need the client to watch its own usage and race a new purchase against exhaustion — real work, and the demo doesn't need it (see billing model above).
- **ENS-published data-relay discovery.** Resolved separately, Sept 10 2026 — see `adr/0003`'s Consequence section.
- **Rendezvous-token purchase following the relay set.** `sidecar.Config.RendezvousPaymentURL` is one fixed URL; `rendezvous.ExchangeAny` fails over across rendezvous addresses but token purchase doesn't follow it, so a node can't authenticate to a *surviving* metered relay once the one its token-buying is pinned to is dead. Found by the Sept 10 live run (below); real work (mirror `ExchangeAny`'s per-address retry in the token-purchase path), not attempted this pass.

## Kill-mid-transfer failover — closed Sept 10, 2026

The liveness signal is `wgnode.PeerInfo.RxBytes` (wireguard-go's own UAPI `rx_bytes=` counter, confirmed against the vendored source, not the handshake timestamp originally considered — a session's data key stays valid for minutes without a fresh handshake, so "no new handshake" would notice a dead relay far slower than "received bytes stopped moving"). `brambled/datarelay.WaitForStall` polls it every `dataRelayPollInterval` (2s) and blocks until it hasn't grown for `dataRelayStallTimeout` (6s) — deliberately can't distinguish "relay died" from "nothing to send right now," which is fine specifically because Gate 4.3's own test is "kill it *mid-transfer*": there's always traffic in flight exactly when the signal needs to fire.

**Asymmetric by design, matching the Decision section above: only the flagged side buys.** `brambled/main.go`'s `watchDataRelayFailover` is one background goroutine per `-relay-peer`, started once at `serve` startup: it waits for the peer's first successful connect (recorded in a small shared `relayState`, keyed by tracked-peer label so a key rotation carries over automatically), then blocks on `WaitForStall`, and on a real stall buys a fresh session and re-points this node's own peer-endpoint directly — `admission.Loop`'s `EndpointResolver` only fires once per pubkey for the life of the `Loop`, so nothing else would ever re-resolve it. The non-flagged side of the pair never buys anything; it runs `watchDataRelayAdopt` instead, which stays continuously present at the rendezvous relay (a short `rendezvous.ExchangeAny` call every few seconds, not a single long-lived one — `Exchange` is one-shot rendezvous, not a subscription, so a long call can end up adopting whichever offer happens to be in flight when its own ack lands rather than the most recent one) and re-points itself whenever the candidate it learns actually changes.

That asymmetry isn't a simplification for the test — it's load-bearing. A first version of both the test and this ADR had *both* sides of the pair buy independently on every failover, mirroring how the initial-connect test was written. **A live run against the real `relay` binary broke that immediately**: a real relay hands out a fresh UDP port per session bought (the whole point of "port-per-session" above), so two independent purchases for the same logical connection land on two different, unconnected sockets — nothing forwards. The original fake test sidecar masked this by returning the same fixed port for every call to a given sidecar URL, which a real relay never does. Fixing the test's fake relay to allocate a genuinely fresh port per call (matching the real one) turned this from "found by luck in a live run" into a pinned regression, and surfaced two more real bugs along the way, all now fixed:

- **The adopting side never armed a persistent keepalive.** `SetPersistentKeepalive` was only ever called by the buying side, so the relay's "first two distinct sources become the two slots" learning never saw a packet from the adopting side — nothing to forward to. Fix: both `watchDataRelayAdopt` and the plain (non-relay-peer) `EndpointResolver` branch now arm it unconditionally whenever a data-relay pool is configured at all, since a node has no way to know whether a peer's candidate is relay-routed or a real direct address.
- **Failover's exclusion set only ever excluded the relay currently in use, not every relay tried so far.** `remaining := pool minus usedLabel`, recomputed from scratch on each stall, forgets a relay was already dead the moment a later relay is the one currently in use — a second stall (even a false one, from the peer not having adopted yet) retries the first, already-dead relay forever. Fix: `watchDataRelayFailover` now keeps a persistent `excluded` set for the life of the watcher.

Real test, not just a state-flag assertion: `brambled/datarelay_endpoint_test.go`'s `TestDataRelayFailover_SwitchesToBackupRelayWhenPrimaryStalls` runs two real hand-rolled UDP relays (now allocating a fresh port per session, like the real binary) and two real netstack WireGuard nodes, confirms a real handshake through the cheaper of the two (deterministic via priced quotes, avoiding a coin-flip on identical prices), kills the primary relay for real — including making its fake sidecar refuse new sessions, matching what killing the real process does — mid-ping-loop, and asserts a real WireGuard handshake succeeds again through the backup afterward, converging in a single round.

**Live run status, Sept 10 2026: partially blocked, not yet closed.** Run against the real `relay` binary, two real relay-sidecars at different prices (1 vs. 1000 atomic USDC/byte), a real Hedera testnet payer: the initial connect, both cost-scaling purchases (Gate 4.2), and relay selection (Gate 4.3's other half) all settled real, mirror-node-confirmable payments and are ✅ verified. The kill-mid-transfer half is not: killing the primary relay process also kills its rendezvous TCP listener, and `sidecar.Config.RendezvousPaymentURL` is a single URL fixed at sidecar spawn — so once the primary is dead, this node can no longer buy a rendezvous token *for any relay*, and `rendezvous.ExchangeAny`'s address-list failover has nothing valid to present at the backup's rendezvous port either. This is a fourth, structurally separate gap from the three above: token purchase doesn't follow the relay set the way candidate exchange does. Closing it is new feature work (teaching token purchase to try each configured rendezvous relay's own payment URL, mirroring `ExchangeAny` itself), not a Section D fix, and is scoped out of this pass. Gate 4.3-failover is 🔧 **built and tested** (the mechanism above, proven live down to the token-purchase boundary), not ✅ verified end-to-end on Hedera.

**Incidental finding:** `relay/main.go` has no SIGTERM handler, so a plain `kill` on the process doesn't run its `defer ps.Stop()` — the spawned relay-sidecar (`bun`) child outlives its parent and keeps answering `/price`/`/data-relay-session` on the old port. Hit twice during this live run; worth a signal handler if `relay` is used past the hackathon, not fixed here.

## Rationale

Port-per-session costs a small amount of OS-level bookkeeping (opening/closing one `net.ListenUDP` per session, tracked by a session map) in exchange for completely sidestepping the WireGuard-socket-ownership problem a shared-port design runs into in this codebase. It also keeps the relay's job exactly as dumb as `adr/0003` already established: no per-packet parsing beyond "which slot did this arrive from," no protocol awareness of WireGuard's frame format at all — the relay never needs the discriminator-byte logic that was the original plan, because there's nothing left to discriminate once each session has its own port.

## Consequence

- `relay/main.go` gains `-data-port` (public UDP forwarding range... actually one port per active session, allocated dynamically — no fixed range needed since the OS assigns free ports on `net.ListenUDP(":0")`), `-internal-port` (loopback allocation API), and `-price-per-byte`.
- `relay-sidecar` needs the Go relay's internal-API URL passed through the same env-var handoff `adr/0007` already established for `RENDEZVOUS_TOKEN_SECRET`.
- `05_BUILD_PLAN.md` Gate 4.2 and Gate 4.3's selection half: ✅ verified by the Sept 10 live run above (real settlements of different sizes, real relay selection between two differently-priced real relay-sidecars). Gate 4.3's failover half: 🔧 built and tested against real UDP relays and real WireGuard nodes, blocked short of a full live-Hedera run by the token-purchase gap named above and in "Explicitly out of scope."
