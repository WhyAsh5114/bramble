# ADR 0006 — Gateway CONNECT protocol, peer-identity resolution, and client forwarding

**Status:** Decided and verified, Sept 8 2026. `HARD GATE 2.3` (`docs/05_BUILD_PLAN.md`) passes end-to-end against a real WireGuard tunnel — `brambled/gateway/server_test.go`'s `TestGate2_3_AgentCannotReachOutsideACL`. The client-side counterpart (`Forwarder`, below) is verified both locally and against a real second machine over the real internet (`brambled/README.md`'s "Client forwarding runbook").

## Context

`adr/0005-acl-record-schema.md` built the on-chain schema (Section B): a device's `acl` record holds ECDH digests, a gateway's own `acl-granters` record lists whose vouches it trusts. That ADR named a specific list of things it deliberately left unbuilt — "What Section C still owns": the listener itself, `CONNECT <service>` parsing, local service→port config, the verification loop, and a way to know which device an inbound connection is from. This ADR covers those, plus one correction to ADR 0005's own speculation.

## Design

**Protocol: a single fixed port, one line, then raw bytes.** A peer connects over the tunnel to the gateway's fixed `-gateway-port` (default `7891`), sends `CONNECT <service-name>\n`, and gets back either `OK\n` followed by the proxied backend's bytes, or `DENY\n` followed by connection close. No framing beyond that — this isn't HTTP CONNECT, just the minimal thing that lets one TCP listener serve arbitrary local services by name.

**Identity is never self-declared.** The `CONNECT` line carries only a service name, never a claimed identity — the requester's label is looked up from `conn.RemoteAddr()`'s IP against a `tunnel-IP → label` map built from the same static `-peer label=allowed-ip/prefix` config `admission.Loop` already tracks. This is trustworthy specifically because WireGuard's own `allowed_ip` peer binding guarantees a decrypted packet's source IP only ever matches the peer it was configured for (`wgnode.AddPeer`'s doc comment) — a connection that reaches the gateway's listener at all has already passed WireGuard-level admission under a specific, unspoofable peer identity.

**Correction to `adr/0005`:** that ADR speculated Section C would need "a pubkey→label reverse lookup, derivable from the admission Loop's already-tracked Peers/knownPubkeys." Unnecessary in practice — the static `AllowedIP → Label` mapping from `-peer` flags already answers "who is this" directly, with no pubkey involved at all. `gateway.Server.PeerLabels` is that map, built once from the same already-parsed peer list `main.go` hands to `admission.Loop`.

**No redundant admission check inside the gateway.** A `CONNECT` arriving at all already implies WireGuard admitted the peer — `sidecar/client.go`'s existing comment ("mesh admission and ACL enforcement are separate checks") holds structurally: `gateway.Server` only ever runs `CheckACL`, never re-checks admission.

**Listener binding is mode-dependent, mirroring `wgnode`'s own real-OS-TUN/netstack split:**
- Real OS TUN (the default): a plain `net.Listen("tcp", "<tunnel-ip>:<gateway-port>")`. This needed no `wgnode` changes — a real OS TUN interface is kernel-visible, so any ordinary Go listener bound to its address works without special support.
- Netstack (tests/CI): the already-existing `wgnode.Node.ListenTCP`.

**Verification loop (`gateway.CheckACL`)** implements `adr/0005`'s algorithm directly: resolve the gateway's own `acl-granters`; for each trusted granter label, resolve its pubkey, compute `ACLDigestECDH(gateway's own private key, granter's pubkey, serviceName)`, check membership in the requester's `acl`. An unresolvable granter is skipped, not fatal — a transiently-broken granter shouldn't block a different, valid one (mirrors `admission.Loop`'s fail-open-per-label posture).

**`gateway.ACLDigestECDH` is a byte-for-byte Go port** of `admincli/src/roles.ts`'s `aclDigestECDH` — `golang.org/x/crypto/curve25519.X25519` (already a transitive dependency via `wgnode`) for the shared secret, `golang.org/x/crypto/hkdf` (same module, no new dependency) for `HKDF-SHA256(info="bramble-acl-v1")`, stdlib `crypto/hmac`+`crypto/sha256` for the digest. Parity isn't assumed — `gateway/digest_test.go` hardcodes a test vector generated by actually running the TS implementation once with fixed inputs, so a future divergence between the two implementations fails a test rather than silently breaking cross-process agreement between a granter and a gateway running different halves of the stack.

**Local service config is exactly that — local.** `-service name=port` (repeatable, mirrors `-peer`'s flag style) maps a symbolic name to a `127.0.0.1` port on the gateway's own host. Never published on-chain, never read from ENS — `adr/0005`'s Q1 answer ("the receiving peer maps a name to a local port using its own local config") implemented literally. Omitting `-service` entirely means the node offers nothing; every `CONNECT` gets `DENY`.

**The gateway's own identity.** `-label <own-label>` (new, required for `serve`) is what `gateway.Server` resolves to read its own `acl-granters` record. `serve` previously had no notion of its own ENS label at all — only a raw derived pubkey. `PrivateKeyHex` (the node's existing WireGuard private key) is reused directly as the ECDH identity key — no second secret, consistent with `adr/0005`'s "WG keys are the PKI substrate."

## The client-side gap, and why it matters

Everything above verified that the *gateway* enforces correctly — including, in a manual real-Postgres/real-Node test (`realservice_manual_test.go`), that the proxy is genuinely protocol-blind. But every one of those tests hand-wrote the `CONNECT <service>\n` preamble in test code before speaking the real backend's protocol. **No real, unmodified client — `psql`, an agent's Postgres driver, a plain `fetch()` — has any idea that preamble exists.** Without something to inject it on the client's behalf, nothing built so far actually lets an ordinary local service transparently reach an ACL'd mesh service. This is the gap `gateway.Forwarder` closes.

## A real correctness bug, found and fixed while designing the client side

`Server.readRequest` parsed the `CONNECT` line with a `bufio.Reader` wrapping `conn`, then `handle` proxied using the *raw* `conn` — a different reader. `bufio`'s `fill()` reads however many bytes are available in one syscall, which can include bytes past the line if a client's first write ever contains more than just `CONNECT <service>\n` (a legitimate pipelining optimization — write the preamble and the payload in one syscall to save a round trip). Those extra bytes would sit buffered inside the now-discarded `bufio.Reader` and never reach the backend, silently corrupting the stream.

Fixed by having `readRequest` return the `*bufio.Reader` it used, and introducing `bufferedConn` (`server.go`): a small wrapper that reads from the already-primed `bufio.Reader` while writes/close/deadlines still go straight to the underlying `net.Conn`. `net.Conn` already declares `Read`, so embedding both `io.Reader` and `net.Conn` is an ambiguous selector in Go — `bufferedConn` overrides `Read` explicitly instead. `proxy`'s signature widened from `net.Conn` to `io.ReadWriter` to accept it. No behavior change for any existing test (none pipeline past the line today), but `Forwarder`'s own tunnel-side read (below) needs the identical fix, so it was worth closing here rather than letting the client inherit it.

## `gateway.Forwarder` — the client-side counterpart

A local TCP listener (`Listener`) that speaks nothing but plain TCP to whatever connects — the whole point being that it doesn't need to speak anything else. Per accepted local connection: `DialTunnel()` (a caller-supplied func — a plain `net.Dial` to the peer's tunnel address for a real OS TUN node, or `wgnode.Node.DialTCP` in netstack mode) opens one connection to the target gateway, writes `CONNECT <service>\n`, reads one status line. `OK` proxies (through the same buffering-safe `bufferedConn`/`proxy` as the server side); anything else just closes the local connection — the real client sees an ordinary connection reset, indistinguishable from the port simply refusing it.

Lives on `serve` as a new repeatable flag, `-forward <local-port>=<gateway-label>:<service>` — not a separate one-shot subcommand, because a device already runs `serve` to be a mesh member at all, and that process already holds the tunnel, the peer table, and this node's identity. `<gateway-label>` must also be a tracked `-peer`; `serve` fails fast at startup otherwise. The local listener (`net.Listen("tcp", "127.0.0.1:<port>")`) is *always* a real OS socket, regardless of whether this node's own tunnel is real-OS-TUN or `-netstack` — only the tunnel-side dial differs. This matters for how the real run below was actually executed (see there).

## Verified

`brambled/gateway`'s test suite (`go test ./gateway/...`) covers, in increasing order of realism:
- Digest parity against the TS reference implementation, and ECDH symmetry with fresh keypairs (`digest_test.go`).
- `CheckACL`'s trust-store logic against a fake resolver — trusted-granter allow, untrusted-granter ignore, wrong-service deny, cross-gateway digest non-portability, empty-ACL deny, unresolvable-granter-is-skipped-not-fatal (`acl_test.go`).
- `TestGate2_3_AgentCannotReachOutsideACL` (`server_test.go`) — Gate 2.3's actual required test, three real peers (netstack, real WireGuard handshakes, real TCP over the tunnel, real local backend processes): a `db`-only device's `CONNECT db` on its authorized gateway succeeds and proxies real bytes end to end; `CONNECT cache` on the same gateway is denied; `CONNECT db` on a *different*, separately-keyed gateway that also trusts the same granter is denied — proving digest non-portability with real code, not just the unit-level claim in `acl_test.go`.
- `TestForwarder_PlainClientProxiedThroughACL` (`forward_test.go`) — a genuinely plain `net.Dial` client (no CONNECT knowledge at all) proxied through to a real local backend and back; the denial counterpart closes the local connection with zero bytes.
- `realservice_manual_test.go` (`//go:build manual`, excluded from `go test ./...` — needs live Docker/Node processes first) — the gateway side against a real Postgres container and a real Node HTTP server, both allow and deny paths.

Full `brambled` suite (`admission`, `gateway`, `rendezvous`, `sidecar`, `wgnode`) green, no regressions from any of the above, including the buffering fix.

**Real two-machine run, Sept 8 2026 — pass.** Not simulated: a laptop and a real AWS EC2 instance (`ap-south-1`, arm64), two freshly enrolled real devices on the dev tailnet (`vps-demo`, `laptop-demo`), a real `acl`/`acl-granters` digest pair written on-chain (granter: the already-enrolled `device1`), a real relay-mediated candidate exchange over the actual internet. An ordinary, completely unmodified `curl http://127.0.0.1:8080/` reached a real Go HTTP server on the VPS and got its real response back — laptop → relay → WireGuard tunnel → gateway's `CONNECT` listener → on-chain ACL check → local backend → back. Clearing the on-chain `acl` digest (no restart of either `brambled` process) turned the identical `curl` into a connection reset on the very next request — `CheckACL` resolves fresh chain state per `CONNECT`, so there's no cache to invalidate. Full transcript and reproduction steps: `brambled/README.md`'s "Client forwarding runbook."

## Consequence

- `docs/05_BUILD_PLAN.md` Gate 2.3 flips to verified.
- `brambled serve` gains four new flags: `-label` (required), `-service` (repeatable, optional), `-gateway-port` (default `7891`), `-forward` (repeatable, optional).
- The Section C proxy path (`proxy`, `bufferedConn`) is now correctness-hardened against pipelined client writes, not just against the request shapes today's tests happen to send.
